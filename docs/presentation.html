Airlock

Objective: agent-written code reaches the repo only after it passes checks the agent cannot see or edit. When a bug still gets through, those checks get stricter, but only if an independent evaluation shows the change helps.

Problem
  • Agents aim at whatever the test checks, usually the HTTP status.
  • A status-code test can pass while rows are left half written.
  • When a bug escapes, the tests stay the same, so the next one escapes too.
Application loop: ship the feature
  1. Plan; operator approves the contract
  2. Workers code in disposable checkouts
  3. Freeze output into an immutable artifact
  4. Validate under the active harness
  5. Fenced three-way merge, then re-test
Harness loop: improve the checks
  1. A bug escapes validation
  2. Propose a candidate harness version
  3. Paired eval: baseline vs. candidate on labeled apps
  4. Promote only if escapes drop and valid work still passes

All state, evidence, artifacts and harness history live in MongoDB Atlas.

The harness

A versioned config that decides what "passing" means

harness_versions: v2, green = added over v1
{ "runner": "bulk", "context": { "include_patterns": ["app/**"] }, "tools": { "profile_key": "bounded-items-worker", "publish": "deny" }, "validation": { "required_tags": ["happy_path", "owner_boundary", "idempotency"], "inspections": ["http_responses", "rows_unchanged_on_rejection", "idempotency_semantics"] } } parent_id: hv_v1 config_digest: sha256:... created_by_evolution_run_id: evo_...

Versions are immutable. The project's active pointer selects one, so promoting or rolling back just moves the pointer.

One validation run
  1. Unpack the frozen candidate from GridFS into a fresh directory
  2. Boot the app against a disposable DB, with a stripped env
  3. Trusted driver runs the scenarios selected by required_tags, snapshots affected rows before and after, and emits raw observations
  4. Inspectors named in inspections run controller-side and turn observations into checks
  5. Any fail: repair_required. Observer error, unknown inspector or no checks: inconclusive. Otherwise pass.
Proposer may change
tags, inspector selection, context patterns, worker profile
Proposer may not change
inspector code, eval thresholds, holdout labels, the active pointer
Demo

A partial write that passes v1 and is caught by v2

Delegated feature: PATCH /api/v1/items/bulk

for u in body.updates:
    item = db.items.find_one({"_id": u.id})
    if item["owner_id"] != user:   # checked too late
        raise HTTPException(403)
    db.items.update_one(           # no transaction
        {"_id": u.id}, {"$set": u.fields})

The owner_boundary scenario sends Alice's row, then Bob's. The app returns 403, but Alice's row was already written. v1 only checks the status, so it passes. v2's rows_unchanged_on_rejection diffs the rows and fails it.

The evaluator promotes only if all four hold
  1. Escaped failures strictly decrease
  2. No more blocks of valid work than baseline
  3. Clean build has zero failing checks
  4. Wall-clock within 3x of the parent version

For a reproducible demo, the faulty and fixed builds are planted and the proposer is deterministic. An Agent SDK proposer plugs into the same schema-checked contract; either way, the evaluator decides.

Operated from Claude Code

What holds it together

  • Hooks: while a task runs, PreToolUse denies Edit/Write on the registered repo and ad-hoc subagents. If the API is unreachable, it fails closed.
  • Freeze after stop: output is captured only after the worker exits, as a deterministic tarball hashed into GridFS and verified on read-back.
  • Fail-closed verdicts: an observer error is inconclusive, never a pass.
  • Fencing: a stale integration writer's final write matches zero documents and is dropped.

Not yet: container isolation and scoped DB users, an LLM proposer, a held-out corpus with more defect classes.
