MongoDB Hackathon, October 2026

Airlock

A test harness for AI coding agents that gets stricter every time a bug gets through.

Job state, evidence, code artifacts and harness history all live in MongoDB Atlas.

Problem

Agent-written code can pass its tests and still corrupt data

  • Coding agents now produce code faster than people can review it.
  • They aim at whatever the test checks, which is usually the HTTP status code.
  • A status-code test can pass while rows in the database are left half written.
  • When a bug gets through, the test suite usually stays the same, so the next similar bug gets through too.

Our approach

  1. Freeze the agent's output so it can't change after review starts.
  2. Run it in an isolated sandbox.
  3. Check it against invariants the agent can't edit.
  4. When a bug escapes, propose a stricter harness and keep it only if held-out evals show it catches the bug.
How it works

Two feedback loops, one database

Application loop

Ships the feature

  1. Plan the change
  2. Operator approves the contract
  3. Delegate to isolated workers
  4. Freeze each worker's output
  5. Validate against trusted invariants
  6. Three-way merge, then re-test
Harness loop

Improves the tests

  1. A bug escapes validation
  2. Propose a stricter harness
  3. Run a paired eval on held-out cases
  4. Promote if it catches the bug and blocks no valid work
  5. Otherwise roll back

The test policy is what improves over time. A separate evaluator decides whether each change is promoted.

Demo

A partial write that passes the test

Delegated feature: PATCH /api/v1/items/bulk, an atomic bulk update with idempotency keys.

Planted bug
for u in body.updates:
    item = db.items.find_one({"_id": u.id})
    if item["owner_id"] != user:   # checked too late
        raise HTTPException(403)
    db.items.update_one(           # no transaction
        {"_id": u.id}, {"$set": u.fields})

In a batch with mixed owners, Alice's row is written first. The loop then reaches Bob's row and returns 403, but Alice's row has already changed.

Why harness v1 misses it

  • v1 only checks the HTTP status, and 403 is the correct status.
  • It never compares the database before and after the request.
  • The test passes while the data is wrong.

Catching it takes a mixed-owner batch plus a before/after snapshot of the affected rows.

Hypothesis from the evolver: mixed-owner batches with a before/after database check will catch the partial write that the status-only harness misses. The evolver generated and logged this; nobody edited the policy by hand.

Promotion

v2 is promoted only on held-out results

v2 and v1 are evaluated side by side on the same frozen apps, with 3 fresh seeds per app. New canary salts on every run prevent memorization.

A separate evaluator decides eligibility. The evolver can propose changes within a fixed limit, but it can't promote its own proposals or see the holdout labels.

Promotion requires all four
  1. Escaped failures strictly decrease
  2. Valid work still passes (0 false blocks)
  3. The clean app never regresses
  4. Overhead stays within 3x of baseline

Implementation

What makes it reliable

Freeze after stop

Worker output is captured only after the entire process tree has exited. A finished worker is not automatically accepted.

Content-addressed artifacts

Deterministic tarballs (mtime=0) are hashed, stored in GridFS and read back to verify. The same input always gets the same ID.

Fail-closed validation

If an observer errors, the result is inconclusive, never a pass. Verdicts are cached by an exact input key.

Serial three-way merge

git merge-file per file with one fenced writer, so at-least-once delivery can't duplicate or overwrite changes.

CAS, fencing, epochs

Leases, revision compare-and-set, integration fences and constraint epochs. Stale work is rejected before it's applied.

Trusted inspectors

Every check runs in the controller, never in candidate code. Credentials are replaced with canary hashes.

Interface

Runs inside Claude Code

  • Plugin and MCP bridge expose airlock_plan airlock_status airlock_delegate as tools.
  • PreToolUse hook blocks direct writes to the registered repo and ad-hoc subagents while a task runs, so only managed workers write code.
  • Stop hook keeps the session open until the task finishes.
  • Live dashboard shows validation results, the evolver's hypothesis and the before/after row behind each failure.
