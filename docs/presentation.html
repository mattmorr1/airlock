MongoDB Hackathon · Oct 2026

Airlock

A self-improving harness for untrusted AI coding agents.

The agent ships the feature. The harness learns to test it.

Everything — state, evidence, artifacts, harness history — runs on MongoDB.

The problem

AI agents write code that passes the test and breaks the data

  • We let coding agents write and merge code faster than anyone can review it.
  • They optimize for the test passing — not for the behavior being correct.
  • A status-code test goes green while the database is quietly corrupted.
  • When a bug escapes, nobody strengthens the test suite — so the same class of bug escapes again.

The core idea

Treat the agent's output as untrusted:

freeze it

run it in isolation

judge it against invariants it can't weaken

and when a bug escapes — evolve the test policy and prove the fix

What Airlock is

Two loops around one source of truth

① Application loop

Ship the feature, safely.

plan → approve contract
→ delegate to isolated workers
→ FREEZE each output
→ validate vs trusted invariants
→ 3-way integrate + re-test
→ verified result

② Harness loop

Improve the tester, not just the code.

a bug escaped?
→ hypothesize a stricter harness
→ paired eval on held-out cases
→ promote only if it catches the bug
   without failing legit work
→ else roll back

The thing that self-improves is the test policy — judged by an evaluator it cannot game.

Two planes, zero shared code paths — they communicate only through documents on the jobs queue. The target app under test runs on its own separate Mongo.

The demo

A half-line bug that passes the test

Delegated feature: PATCH /api/v1/items/bulk — atomic bulk update with idempotency.

The planted bug: partial write

for u in body.updates:
    item = db.items.find_one({"_id": u.id})
    if item["owner_id"] != user:   # check too late
        raise HTTPException(403)   # ...Alice already written
    db.items.update_one(           # no transaction
        {"_id": u.id}, {"$set": u.fields})

A mixed-owner batch writes Alice's row, then hits Bob's and returns 403 — but Alice's row is already corrupted.

Why status-only tests miss it

  • Harness v1 checks: did it return the right HTTP code? ✓ 403
  • It never looks at the database before vs. after.
  • Test is green. Data is wrong. The bug escapes.

An independent probe — a mixed-owner batch + a before/after DB snapshot — is what actually catches it.

The payoff

The harness evolves: v1 → v2

v1 — status only

inspections = ["http_responses"]
required_tags = ["happy_path"]

Faulty app → PASS (bug escapes)

v2 — + database invariants

inspections = ["http_responses",
  "rows_unchanged_on_rejection",   # NEW
  "idempotency_semantics"]         # NEW
required_tags = ["happy_path",
  "owner_boundary", "idempotency"] # NEW

Faulty app → REPAIR_REQUIRED (bug caught)

Hypothesis (logged, deterministic — not hand-edited): "Mixed-owner batches plus a before/after database invariant catch the partial write that a status-only harness lets through."

Proof, not vibes

Promoted only on held-out evidence

Candidate v2 runs a paired evaluation against baseline v1 — same frozen apps, 3 fresh seeds each (fresh canary salts, so it can't memorize).

An independent evaluator decides eligibility. The evolver only proposes within a fixed ceiling — it never promotes itself, and never supplies the holdout labels.

Promote iff ALL four hold:

  • escaped failures strictly decrease
  • legitimate work still passes (0 false blocks)
  • clean app never regresses
  • overhead ≤ 3× baseline

End to end

One request, proven the whole way down

you type a request in Claude Code → plan (LLM planner, Agent SDK) → operator approves the contract digest → delegate assignments → isolated workers write code → FREEZE each output (after the process tree is stopped) → VALIDATE in a sandbox vs trusted invariants ← faulty caught under v2 → repair → 3-way integrate + re-test → completed └─ a failure escaped? → propose stricter harness → paired holdout eval → promote (3→0) → repaired code passes

Proven live on Atlas through the real HTTP API — plan → approve → delegate → validate → repair → integrate → evolve → promote.

Under the hood

The hard parts we actually built

Freeze-after-stop

Worker output is captured only after the whole process tree is killed. finished ≠ accepted.

Content-addressed artifacts

Deterministic tarballs (mtime=0) → tree hash → GridFS with read-back verify. Same input, same ID.

Fail-closed validation

Any observer hiccup ⇒ inconclusive, never PASS. Verdicts cached by exact-input key.

3-way serial integration

git merge-file per file, fenced single-writer — at-least-once delivery can't duplicate or clobber.

CAS + fencing + epochs

Leases, revision CAS, integration fences, constraint epochs — stale work is rejected, not applied.

Trusted inspectors

Judgment lives in the controller, never in candidate code. Credentials redacted to canary hashes.

The front door

It drives from inside Claude Code

  • Plugin + MCP bridge: airlock_plan / status / delegate as native tools.
  • PreToolUse hook: while a task runs, blocks writes to the registered repo and ad-hoc subagents — the managed workers are the only writers.
  • Stop hook: won't let the session quit mid-task.
  • Live dashboard: validation verdicts, evolution hypothesis, and the actual before/after row that proves the catch.
